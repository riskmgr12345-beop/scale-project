# 저울 (Scale Project)

각 종목이 "오를 이유"(부스터: 거래량비, 최근 빠른반등 이력)와 "내릴 이유"(위험신호: 당일 급반등)를
저울질해서 순점수(-5~+5)로 계산하고, 코스피+코스닥 전체(약 2,700종목) 중 상위 후보를 뽑는
리서치 프로젝트입니다.

## 배경

V3(`stock-autotrading-v3`)의 ZZ 되돌림 전략에서 49종목/8년 데이터로 검증한 "줄다리기" 공식을
그대로 코스피+코스닥 전체에 적용했더니, 방향성(강한이김≥2점이 낫다)은 재현됐지만 절대 수치는
많이 달랐습니다(`scale_validation_result.txt` 참고). 그래서 같은 공식이라도 유니버스가 다르면
별도로 검증·관리해야 한다는 원칙 아래 "저울"이라는 별도 이름/프로젝트로 분리했습니다.

## 데이터 소스

`limitup-precursor-research`(콜라 프로젝트, https://github.com/riskmgr12345-beop/limitup-precursor-research)
가 매주 자동 갱신하는 `research_cache/limitup_ohlcv_cache.pkl`(코스피+코스닥 전체 OHLCV)을
읽기전용으로 재사용합니다. 이 저장소 자체는 시세 데이터를 직접 수집하지 않습니다.

## 파일

- `scale_validation_test.py`: 저울 공식(부스터-위험신호)이 코스피+코스닥 전체에서도 통하는지
  검증한 스크립트 (n=77,750, 강한이김/약한이김/비김/짐 4분류 + 시기분할 재현성 확인).
- `render_scale_report.py`: 상위 15개 종목을 뽑아 보고서(`scale_top15_report.txt`)를 생성하는
  본 프로덕션 스크립트.

## 향후 과제

- 종목현황(52주위치·관리종목·PER 포함됨, 수급은 미포함) 확장 -- 다음은 수급비율(④).
  (관리종목/재무위험/PER은 아래 두 섹션으로 완료)
- 클라우드 에이전트로 매일 자동 실행 + 보고. (완료 -- "저울 프로젝트 일일 리포트" 라우틴)
- 생존편향(상장폐지 종목이 캐시에 없음) 미해결 -- 다음 검증 우선순위.

## PER/관리종목 여부 (2026-09-05, V3 ZZ "객관가치" 배지 포팅)

ZZ의 "객관가치" 배지(가격위치+수급+PER/관리종목)에서 PER·관리종목 부분을 저울에 포팅했습니다.
ZZ는 KIS 실시간 API(`get_current_price`, 인증된 실계좌 세션 필요)로 이 값을 얻는데, 저울은
GHA 배치라 그런 세션이 없습니다. pykrx로 대체를 시도했으나 **KRX가 OTP 발급 단계에서 막아
로컬에서도 전부 실패**(날짜와 무관하게 재현 -- 현재 pykrx 자체가 불안정한 상태로 보임).

대신 `FinanceDataReader.StockListing('KRX')`의 `Dept` 컬럼에 "관리종목(소속부없음)"/
"투자주의환기종목(소속부없음)"이 그대로 들어있어 **인증 없이 동일 정보**를 얻을 수 있었습니다.
PER은 시가총액 ÷ DART 당기순이익(이미 캐시된 값 재사용, 신규 API 호출 없음)으로 계산 --
KIS의 EPS 기반 PER과 정의는 동일하고 발행주식수 대신 시총을 바로 쓸 뿐이라 오차 없습니다.

**오늘 실측**: 강한이김 20개 중 **4개(20%)가 KRX 공식 관리종목/투자주의환기 지정**에
걸림 -- DART 재무경고(35%)와는 별개의 신호입니다. 그중 수성웹툰(084180)은 저울점수 +3
(강한이김)이면서 **동시에 상장적격성 실질심사 대상 + 거래정지 상태**였습니다(원풍물산류
리스크의 또 다른 실사례). "✅ 강한이김 + 재무경고 없음" 박스의 필터 조건에 이 두 KRX
공식 지정도 추가해서, 최종적으로 9/20개만 통과합니다.

## DART 재무경고 + 최근 60일 공시 (2026-09-05, V3/콜라 기능 포팅)

사용자 요청("v3, 콜라, 환타, zz 등에서 분석 적용한 내용중 저울에 적용 도움되는 내용 모두
검토" -> "순서대로 시작해")으로, 콜라 프로젝트(limitup-precursor-research)에 이미 있던 DART
연동 2가지를 포팅했습니다:

1. **재무경고**(`dart_risk_check.py`) -- 완전자본잠식(자본총계≤0) 또는 3년 연속 당기순손실을
   DART 재무제표로 선행 경고. 계기는 콜라의 원풍물산 사례("패턴은 맞는데 회사 자체가 위험한"
   개별 종목 -- 3년 연속 적자, 그것도 악화 중인데 조사 당시 아직 공식 관리종목 지정 전이라
   가격·거래량 통계로는 전혀 안 잡혔음). **오늘 실측**: 강한이김 20개 중 **7개(35%)가 이
   경고에 걸림** -- 저가주 리스크가 실제로 유의미한 비중임을 확인.
2. **최근 60일 이벤트성 공시** -- 정기공시(사업보고서 등)는 제외하고 자기주식취득·투자유의
   안내 같은 이벤트성 공시만 캐시에 저장(화면 표시는 다음 단계).

**적용 범위**: 콜라는 하루 후보가 10~20종목대라 전부 조회해도 부담 적은데, 저울은 2,700종목
규모라 **오늘 상위 20개(강한이김 후보)에만 한정** 적용합니다(전체 스캔 안 함).

**화면 반영**: 재무경고 있는 종목엔 💸 배지, 그리고 강한이김 박스 위에 "✅ 강한이김 +
재무경고 없음" 박스를 추가로 만들어 리스크까지 거른 최종 후보를 따로 보여줍니다.

**구현**: V3의 `infra/dart_client.py`(콜라가 로컬 절대경로로 import)와 달리, GHA/클라우드
어디서든 동작하도록 DART API 호출 로직을 `dart_risk_check.py`에 자체 포함(self-contained)
시켰습니다. 별도 GHA(`refresh_dart_risk.yml`, 매일 07:55 UTC)가 담당 -- **저장소 시크릿에
`DART_API_KEY` 등록 필요**(opendart.fss.or.kr에서 발급).

## 버그: touch_depth_now가 검증 공식과 다르게 계산되던 문제 (2026-09-04, 사용자가 확대차트의
과거 터치 3건 vs 오늘 터치 1건을 직접 비교하다 발견)

과거 터치 마커(`_historical_touch_points`)는 검증 스크립트와 동일하게 "다리 고점 대비 그날
저가"로 depth_pct를 계산하는데, 오늘(라이브)의 depth_pct를 만드는 `touch_depth_now`는
`(오늘 종가/오늘 저가-1)*100`(오늘 하루의 자체 반등폭)으로 **전혀 다른 공식**을 쓰고 있었습니다
-- 상위 20개 필터링·순위에 실제로 쓰이는 값이 검증된 정의와 안 맞았던 진짜 버그입니다. 예:
로체시스템즈 09-03 -- 버그 있던 값 2.5%p(오늘 반등폭) vs 올바른 값 6.83%p(다리 고점 6,880원
대비). `pos["leg_start_price"]`(다리 시작 고점) 기준으로 고쳐서 `_historical_touch_points`와
공식을 통일했습니다. 고친 뒤 전체 후보군이 537종목→1,712종목으로 크게 늘었고(진짜 깊은
되돌림이 더 정확히 잡힘) 상위 20개 순위도 전면 교체됐습니다. **`scale_validation_test.py`
자체는 처음부터 올바른 공식을 썼으므로 검증 수치(72.8%/+0.49% 등)는 영향 없음** -- 이번
버그는 라이브 리포트(`render_scale_report.py`)에만 있었습니다.

## 버그: 진행 중인 다리가 "지금 다리"가 아니라 "그 전전 다리"를 보여주던 문제 (2026-09-04,
사용자가 "오늘 3% 다리가 생긴게 3개 맞지?"를 확인하다 발견)

`zigzag_swings()`가 반전(3%+ 되돌림)이 **확정된 시점에서만** 스윙점을 기록하고, 확정 이후
같은 방향으로 계속 움직여도(반전 없이) 마지막 스윙점을 갱신하지 않는 구조였습니다. 그 결과
`current_position()`이 돌려주는 (leg_start, leg_end)가 실제로는 "**진짜 현재 다리가 아니라
그 직전에 확정됐던 다리**"였습니다. 예: 뷰노는 08-12(고점 8,180원)부터 진짜 하락다리가
시작해서 09-02(5,210원)까지 -36% 빠졌는데, 화면엔 "다리 2일째, -3.5%"(08-10→08-12의 아주
작은 초기 확정 구간만)로 나오고 있었습니다 -- 그 뒤 3주간의 진짜 하락은 화면에 전혀
반영되지 않았습니다.

V3(실계좌)의 진짜 지그재그(`reporting/charts.py._zigzag_swings`)와 대조해서 원인을 확인:
V3는 루프가 끝난 뒤 마지막에 무조건 한 번 더 "지금까지의 최신 극값"을 append해서 진행 중인
다리를 항상 최신 상태로 유지합니다 -- 이 저장소로 로직을 옮겨 적을 때 그 한 줄을 빠뜨렸던
것이 원인이었습니다(V3 자체는 이 버그 없음, 별도 확인 완료). `zigzag_swings()`에 동일한
마지막 append를 추가해서 수정했습니다.

**영향**: `touch_depth_now`가 쓰는 `pos["leg_start_price"]`(다리 시작 고점)도 잘못된 값이었기
때문에, 상위 20개 순위 자체가 부정확했습니다(고친 뒤 후보군 1,712→1,506종목, 상위 20개
거의 전면 교체). **`scale_validation_test.py`의 검증 수치(72.8%/+0.49% 등)는 영향 없음** --
그 스크립트는 항상 "이미 반전이 확정된, 완결된 다리"만 골라서 쓰기 때문에(`find_touch_
entries`가 확정된 스윙쌍만 순회) 이 "아직 안 끝난 마지막 다리" 버그가 애초에 낄 자리가
없었습니다. 라이브 리포트(`render_scale_report.py`)에만 있던 버그입니다.

## 강한이김(≥2점) 안에서 확률을 더 올리는 방법 검증 (2026-09-04)

강한이김(≥2점, n=16,127~77,750) 모집단 안에서 확률을 더 높일 방법 3가지를 검증했습니다.
방법론은 동일: 최소표본 15건, 시기분할(전/후반부) 재현성, 도달률뿐 아니라 실제수익률.

**① 시장국면(코스피 60일선) 필터 -- 채택, 프로덕션 반영 완료.** 코스피 종가가 자기 60일
이동평균 위(상승장)/아래(하락장)냐로 나눠보니:
- 상승장: 강한이김 5일도달률 69.7%, 평균 -0.26%
- 하락장: 강한이김 5일도달률 **79.3%**, 평균 **+2.06%**

반직관적이지만(시장 전체가 눌려있을 때 개별종목 반등신호가 더 잘 맞음), 시기분할 둘 다 같은
방향으로 재현됨(`regime_filter_result.txt`/`regime_timesplit_result.txt`). 국면 데이터는
`build_kospi_regime_cache.py`가 GHA로 매일 미리 조회해 `research_cache/kospi_regime_cache.json`
에 캐시하고(클라우드 라우틴 네트워크 제약 우회), `render_scale_report.py`가 화면 상단에
배지로 표시합니다.

**② 유동성(진입 직전 20일 평균거래대금) 필터 -- 기각.** 3분위로 나눠도 유동성 낮은 쪽이
오히려 근소 우위(74.1% vs 72.0%)였고, 거래대금 하한선을 1억→30억원까지 올려도 거의 안
움직였습니다(71.9~72.9%). 시기분할하면 방향이 아예 뒤집혀서(전반부: 하위1/3이 우위 /
후반부: 거의 동률) 재현 안 됨으로 결론. "저유동성 소형주가 노이즈 원인"이라는 가설은 이
방식으로는 뒷받침되지 않았습니다.

**③ 되돌림깊이(depth_pct) 구간별 세분화 -- 기각(근거 약함).** 7~10%p(73.3%) / 10~15%p(71.5%)
/ 15~20%p(75.5%, n=417) / 20~30%p(63.6%, n=151) / 30%p+(70.8%, n=24)로, "깊을수록 좋다"는
단조 패턴이 아니었습니다. 특히 30%p+의 평균수익 +35.96%는 표본 24건 중 극단값 1~2개에
좌우된 것으로 보여 신뢰 불가. 얕음(7~10%p) vs 깊음(20%p+)의 시기분할도 완전히 뒤집힘
(전반부 -3.55% vs 후반부 +10.04%) -- 재현 안 됨.

`regime_filter_test.py` (`regime_filter_result.txt`/`regime_timesplit_result.txt`).

## MIN_DEPTH(진입 문턱) 스윕 검증 + 사이트 기본값 2%→10% 변경 (2026-09-05)

강한이김(≥2) 조건에서 진입 문턱(고점 대비 되돌림 깊이) 자체를 7%(검증 baseline)에서
10%/12%/15%/20%/25%/30%로 올려가며 확률·수익률 변화를 검증했습니다.

| 문턱 | 표본 | 도달률 | 평균수익 | 전반부 | 후반부 |
|---|---|---|---|---|---|
| 7% | 16,127 | 72.8% | +0.49% | — | — |
| **10%** | 12,695 | 73.7% | +1.07% | +0.98% | +1.16% |
| 12% | 10,157 | 74.4% | +1.62% | +1.42% | +1.81% |
| 15% | 7,240 | 76.6% | +2.74% | +2.10% | +3.38% |
| 20%+ | 3,876 이하 | 77~78% | +4~5% | 안정적 | **2~5배 격차** |

**10~12%까지는 시기분할 재현성이 안정적**(전반부/후반부 거의 동일)이라 안전한 개선이지만,
**15% 이상부터는 재현성이 흔들리기 시작**하고 20%+ 이상은 후반부 상위 수익 사례에 거래정지
인접(터치일 거래량0, 5일후 +900%/+373% 같은 가짜값) 데이터 결함까지 섞여있는 걸 직접 확인
-- 정제해도 표본이 수백 건대로 줄어 소수 극단치에 좌우됨. **10%가 안전+효과 둘 다 만족하는
최적점.**

**사이트 반영**: 처음엔 "전체(2%+)/깊은눌림(10%+)" 두 탭으로 만들었으나, 사이트가 원래부터
(최초 커밋 52d48c7) 써오던 `MIN_DEPTH=2.0`(검증 baseline 7%와는 별개로, "후보를 넓게 보고

**`MIN_DEPTH` 자체를 10.0으로 올리고 탭 구조는 되돌려 단일 화면으로 통일**했습니다. 이제
사이트의 강한이김 실측 근거는 "도달률 73.7% · 평균 +1.07%"(n=12,695)입니다.
